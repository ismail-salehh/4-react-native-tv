# Animations

### Use `transform` and `opacity`

Animate only `transform` (scale, translate) and `opacity`. They can run on the GPU without re-layout. Animating `width`, `height`, `top`, `left`, `margin`, or `padding` re-runs layout on every frame and stutters on TV hardware.

- Focus scale: `transform: scale`, not a bigger `width`.
- Sliding menu: `translateX`, not changing `width` or `left`.
- Fade in: `opacity`.

Keep animations short (150–250 ms for focus). The user holds an arrow key and passes 10 cards a second; long animations lag behind the cursor.

### No native driver on web

On native, `useNativeDriver: true` runs the animation on the UI thread, so a busy JS thread doesn't freeze it:

```tsx
Animated.timing(scale, {
  toValue: focused ? 1.08 : 1,
  duration: 150,
  useNativeDriver: true,
}).start();
```

On web there is no native driver. react-native-web warns and runs the animation in JavaScript, frame by frame. If the JS thread is busy (data loading, a big re-render), the animation stutters or skips. For simple focus effects on web, a **CSS `transition`** on `transform` is often smoother than `Animated`, because the browser runs it itself.

### Check nothing stays invisible on old engines (web)

A common pattern: start at `opacity: 0`, then animate to `1`. If the animation never runs or never finishes, the content **stays invisible**:

- An unsupported API or a JS error in the animation code on an old engine.
- `requestAnimationFrame` is paused while the app is hidden or suspended.
- A CSS transition that the engine does not support, so the "end" style never applies.
- The component re-renders and resets the value before the animation completes.

Rules:

- **The resting state must be visible.** Prefer animating *from* a slightly changed state (e.g. `opacity 0.6 → 1`, `translateY 10 → 0`) over starting from fully invisible.
- If you must start invisible, set the final value in the `start()` callback *and* as a fallback timeout.
- Test every screen on the oldest TV you support with animations in mind: does every element show up, every time?

## Explain it out loud

**Why must focus styling never rely on hover alone?**

Because most TV users never hover. Android TV, Apple TV, and Samsung remotes have no pointer, so `:hover` (or `onHoverIn`) never fires for them. If the focus look exists only as a hover style, D-pad users get no visible cursor at all and the app looks frozen.

Hover only happens on some devices, mainly the LG Magic Remote, or a mouse plugged into a box. There, hover should **move focus** to the hovered element, and the element should then show its normal focus style. So the style is driven by the *focused* state, and hover is just one more way to become focused. That way, D-pad users and pointer users always see the same single highlighted element, never two (one hovered, one focused).
