# Screen readers on TV

| Platform | Screen reader | What it reads |
| --- | --- | --- |
| Android TV | **TalkBack** | The focused view: `accessibilityLabel`, role, state |
| Apple TV | **VoiceOver** | The focused view, through the tvOS focus engine |
| LG webOS (web) | **Audio Guidance** | DOM focus and ARIA (`aria-label`, `role`, `aria-live`) |
| Samsung Tizen (web) | **Voice Guide** | DOM focus and ARIA on newer models; check older ones |

### Native (TalkBack, VoiceOver)

The screen reader follows the D-pad focus, so whatever gets focus is read out. Give each focusable element what it needs to be read correctly:

```tsx
<Pressable
  accessibilityRole="button"
  accessibilityLabel={`${item.title}, ${item.year}, ${item.rating}`}
  accessibilityHint="Opens details"
  accessibilityState={{ selected: isSelected }}
  onPress={() => openDetails(item.id)}
>
  <Image source={{ uri: item.poster }} />
</Pressable>
```

- **Poster-only cards need a label.** An image with no text reads as "button" or nothing.
- **Put the useful info in one label** ("Inception, 2010, PG-13"), not spread over five nested `Text`s the reader can't reach (they aren't focusable).
- **Announce changes** that happen without focus moving (e.g. "Added to My List") with `AccessibilityInfo.announceForAccessibility(...)`.
- Check `AccessibilityInfo.isScreenReaderEnabled()` for things like disabling auto-playing trailers or auto-advancing carousels.

### Web (LG, Samsung)

The browser's screen reader follows **DOM focus**. A spatial navigation library may only track focus in JavaScript and draw a style, without moving DOM focus. Then the screen reader hears nothing when the user presses an arrow.

- Make sure the focused element also gets **real DOM focus** (`element.focus()` in the library's `onFocus`, with `tabIndex={-1}` on the element), or announce it through an `aria-live` region.
- Use `aria-label` and `role` the same way as `accessibilityLabel` / `accessibilityRole` (react-native-web maps the RN props to ARIA for you).
- Don't let the browser scroll the page when you call `focus()`. Use `focus({ preventScroll: true })` and scroll your list yourself.

> **Verify (web):** turn on Audio Guidance (LG) and Voice Guide (Samsung) on a real TV and walk through the app. Check the current LG and Samsung developer docs for which platform versions read ARIA and which need a vendor TTS API instead. Also check whether Norigin moves DOM focus in your setup or only tracks it.

### Focus order

The screen reader user can't see the layout; they only hear focus moving. So the order focus moves in **is** the layout for them.

- **Follow the visual reading order:** top to bottom, then start to end. Menu → hero → rails, not hero → rails → menu.
- **Initial focus decides the first thing read.** Put it on the main action (see [Remote and focus](../docs/02-remote-and-focus.md#initial-focus-with-hastvpreferredfocus)).
- **Every focus stop must mean something.** Remove decorative focusables (`focusable={false}`); every extra stop is one more thing read aloud.
- **Give position in lists**: "3 of 12" helps users know where they are in a rail. Add it to the label if the platform doesn't.
- **Modals trap focus** for the screen reader too. Content behind an overlay must not be reachable or read out (`importantForAccessibility="no-hide-descendants"` on Android, `accessibilityElementsHidden` on iOS, `aria-hidden` on web).
- **Don't move focus without the user**, except on screen change, modal open/close, or after an action. Surprise focus jumps are disorienting when you can't see them.
